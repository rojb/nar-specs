## Why

The only guard against a model that keeps calling the same tool is `max_turns` (RRG-63): the request
spends all 20 model calls before saying anything, and every one of them is paid for. It already
happened during the manual runs of RRG-70: one run read the same file three times in a row and
another read it 14 times, each read followed by a compaction the user paid for. The turn limit
neither stops the waste early nor tells the model anything; it only ends the request after the whole
budget is gone.

Failures make it worse. A failing tool returns a bare message, nothing tells the model that the call
it is about to repeat is the one that just failed, and the only structure reaching the model is the
`Error:` prefix the OpenAI-compatible adapter adds. A model that gets the same failure twice learns
nothing new and repeats the identical call.

## What Changes

- **Repeated calls are detected:** within one request, the same tool called with the same arguments
  enough times in a row is a loop, and so is a call pair that alternates A-B-A-B.
- **The model is warned first:** the first detection adds one message generated by `nar` (not by the
  user) that names the repeated calls and asks for a different strategy, then counting starts
  again. The request keeps going, so a model that changes approach is not interrupted.
- **The request stops if it persists:** a second detection in the same request ends the request with
  a clear message. The session continues, the turn budget is not spent, and the history stays valid
  for providers.
- **Structured failure feedback:** the model receives a failing tool result in a fixed envelope
  naming the tool, the failure kind and the message, with one line saying that repeating the same
  call will fail the same way. Repeating a call that already failed is detected sooner than
  repeating a call that worked.
- **The user is told:** both the warning and the stop are reported on standard error, in the same
  place the turn-limit message appears today. Single mode exits with a non-zero code when a request
  is stopped.

Out of scope: a setting to turn detection off or tune it, per-model thresholds, detecting loops in
the model's prose, detecting loops across requests or sessions, undoing the side effects of the tool
calls that ran, and asking a second model to judge whether the agent is looping.

**"Done when" (RRG-71):** an agent that keeps repeating the same tool call no longer spins until the
turn limit: it is told to change strategy and, if it insists, the request stops with a clear message
and the session goes on. Wording taken from `docs/ROADMAP.md`; confirm it against the Linear issue
when linking it (task 0.1).

## Capabilities

### New Capabilities

- `loop-detection`: what counts as a repeated call, the warning to the model, stopping the request,
  the structured failure envelope, and how the user is told.

### Modified Capabilities

None. The change only adds a capability, so it can be archived in any order relative to the changes
that still own `agent-loop`, `tool-framework` and `cli-entrypoint`.

## Impact

- **Code (`nar` repo):** new `src/nar/agent/loops.py`; `src/nar/agent/loop.py` (the detector runs
  after the tool calls of each turn, failing results reach the model in the new envelope);
  `src/nar/agent/events.py` (`LoopDetected`, `LoopAborted`); `src/nar/ui/agent_view.py` (both
  lines); `src/nar/cli/runner.py` (`Outcome.LOOP`); `src/nar/cli/main.py` (exit code); README.
- **Existing tests:** `tests/test_agent_loop.py` gains the loop cases; any test that asserts the
  exact text of a failing tool result the model sees has to expect the envelope.
- **Dependencies:** none new, and no new configuration key.
- **Cost:** no extra model call. A detection adds one message to the history, which the context
  management of RRG-70 can prune or summarize like any other.
- **Specs:** one new capability, no MODIFIED requirements, so no archive ordering constraint.
