## Requirements

### Requirement: Repeated tool calls are detected

Within one request, `nar` SHALL compare the tool calls it executes with the ones executed before them in the same request. A tool called three times in a row with the same name and the same arguments counts as a repetition, where "the same arguments" means the same JSON object, whatever the order of its keys. Calls with a different tool, or with different arguments, SHALL NOT count towards the same repetition. The comparison SHALL start again for every new request and SHALL NOT look at earlier requests or at stored sessions.

#### Scenario: The same read repeated
- **WHEN** the model calls `read_file` with `{"path": "src/app.py"}` three times in a row during one request
- **THEN** the repetition is detected before the next model call of that request

#### Scenario: The same tool with different arguments
- **WHEN** the model reads three different files in a row
- **THEN** no repetition is detected

#### Scenario: A new request
- **WHEN** the user sends a second request after a request that made calls
- **THEN** the calls of the first request do not count towards a repetition in the second one

#### Scenario: Two calls in a turn
- **WHEN** the model asks for the same call twice inside one turn and then again in the next turn
- **THEN** the three calls count as a repetition, because they ran in that order in the same request

### Requirement: Alternating tool calls are detected

Within one request, two calls that keep alternating — A, B, A, B — with the same name and arguments each SHALL count as a repetition once the pattern has completed two cycles. The two calls of the pattern SHALL be different from each other.

#### Scenario: Reading and editing in circles
- **WHEN** the model calls `edit_file` and then `read_file` with the same arguments, twice in a row, without the second edit changing the file
- **THEN** the alternation is detected before the next model call of that request

#### Scenario: A different pair each time
- **WHEN** the model alternates between editing and reading, but the file and the content change every time
- **THEN** no repetition is detected, because the arguments are not the same

### Requirement: The model is warned before the request is stopped

On the first detection in a request, `nar` SHALL add one message to the conversation, generated by `nar` and not by the user, that says which calls are repeating and asks the model to change strategy, and SHALL then start the comparison again. The message SHALL say that repeating the calls will stop the request. The request SHALL continue: the next model call happens as usual and the model may take a different approach. A request SHALL NOT receive more than one such message.

#### Scenario: The model changes strategy
- **WHEN** a repetition is detected and the model then answers or calls a different tool
- **THEN** the request continues normally to its answer and no further warning is added

#### Scenario: The warning is part of the conversation
- **WHEN** the warning has been added and the request continues
- **THEN** the next model call contains the warning, so the model sees the notice together with the tool results that came before it

#### Scenario: Only once
- **WHEN** a repetition is detected again later in the same request
- **THEN** no second warning is added; the request is stopped instead

### Requirement: A request that ignores the warning stops

A detection after the warning was added SHALL end the request before the next model call. The request SHALL end with a message saying that the agent kept repeating the same calls after being warned, naming the calls. The conversation SHALL keep every message of the stopped request, and every tool call SHALL keep its result, so the following request is accepted by the provider. The session SHALL NOT end. In single mode `nar` SHALL exit with a non-zero code.

#### Scenario: Stopped after the warning
- **WHEN** the agent repeats the same call again after the warning
- **THEN** the request ends, the user sees why, the session returns to the prompt and the next request works

#### Scenario: The history stays valid
- **WHEN** a request is stopped by the detection in the middle of a turn with several tool calls
- **THEN** the conversation keeps those calls with their results and the next model call is accepted by the provider

#### Scenario: Single mode
- **WHEN** a request is stopped by the detection in single mode
- **THEN** the message is printed on standard error and the exit code is non-zero

### Requirement: Structured failure feedback

When a tool call fails, the result the model receives SHALL name the tool, the kind of failure and the message of the failure in a fixed format, and SHALL say that repeating the same call will fail the same way and that the arguments or the approach must change. The text the tool produced SHALL appear unchanged inside that envelope. The envelope SHALL be the same for every tool and SHALL reach the model for the failures `nar` already distinguishes: an unknown tool, arguments that do not match the schema, a tool error and an unexpected exception. Tool calls that succeed SHALL NOT change.

#### Scenario: A failing command
- **WHEN** the `shell` tool returns exit code 1 with a message
- **THEN** the model receives the envelope with the tool name, the failure kind, the message unchanged, and the line saying that repeating the call will fail

#### Scenario: Invalid arguments
- **WHEN** the model calls a tool with arguments that do not match its schema
- **THEN** the model receives the envelope with the same list of problems it gets today and the line about repeating the call

#### Scenario: A successful call
- **WHEN** a tool call succeeds
- **THEN** the model receives exactly the output of the tool, without the envelope

### Requirement: Repeated failing calls are detected sooner

A call that repeats the previous call with the same name and arguments and fails SHALL count as a repetition after two calls instead of three, because the model has already been told how it failed. A repetition of a succeeding call SHALL keep needing three.

#### Scenario: The same failing call twice
- **WHEN** the same failing call is executed twice in a row during one request
- **THEN** the warning is added before the next model call

### Requirement: The user is told what happened

The warning and the stop SHALL be reported on standard error as a one-line message each, in the style the turn-limit message uses today, and SHALL NOT write to standard output. The warning SHALL name the repeated calls and say that the agent was asked to change strategy; the stop SHALL name the repeated calls and say that the request was stopped. Markup-like text in a tool name SHALL be printed literally.

#### Scenario: The warning is visible
- **WHEN** a repetition is detected during a request
- **THEN** a line on standard error says which calls repeated and that the agent was asked to change strategy

#### Scenario: Standard output is clean
- **WHEN** a repetition is detected and the model then answers
- **THEN** standard output contains only the answer
